# パイプライン更新報告 (2026-04-24)

2026-04-23 の打ち合わせ内容に基づくパイプライン修正の実施報告です。
打ち合わせ前に実施した BigWig 正規化の修正および FASTQ ダウンロードスクリプトの変更も含みます。

## BigWig の RPM 正規化

以前共有した評価データの BigWig が float 値（RPM 正規化済み）になっていた件を調査しました。原因は旧 CWL パイプラインが deeptools bamCoverage を使用していたためで、現行の `pipeline-v2.sh` は `bedtools genomecov` で生のリードカウント（整数値）を出力していました。

v1 パイプラインと同じ RPM 正規化（reads per million mapped reads）を追加しました:

```
RPM = depth × 1,000,000 / total_mapped_reads
```

`samtools view -c -F 4` で重複除去後のマップリード数を取得し、`awk` で正規化してから `bedGraphToBigWig` に渡します。BigWig の値は float（例: depth=1 で 0.1147）になります。

**注意**: 以前共有した 15 サンプルの BigWig は旧パイプラインの出力で正規化方式が異なるため、今回の新テスト結果で置き換えています。

## FASTQ ダウンロードスクリプトの変更 (`fast-download.sh`)

ChIP-Atlas はエクスペリメント（SRX）単位で処理するため、ダウンロードスクリプトを SRX ID を直接受け付けるように書き換えました。

**変更点**:
- 入力: SRX/DRX/ERX（旧: SRR/DRR/ERR）
- ENA API で SRX → SRR のマッピングを解決（1:N 対応）
- 複数ランがある場合、全 SRR の FASTQ をダウンロード後に `cat` で結合
- gzip ストリームは結合可能なため、再圧縮不要（バイト結合のみ）
- 出力: `{SRX}_1.fastq.gz` / `{SRX}_2.fastq.gz`（PE）、`{SRX}.fastq.gz`（SE）

**ダウンロードルーティング**:
- DRR: NIG ローカルの DDBJ bz2 → ENA HTTPS → fasterq-dump
- ERR/SRR: ENA HTTPS → fasterq-dump

## ChIP-seq パイプライン (`pipeline-v2.sh`)

### 1. Single-end / Paired-end の処理分岐

SE リードでは `samtools collate` / `samtools fixmate` が不要（メイトペア情報を扱うステップ）のため、SE/PE で処理パイプを分岐するようにしました。

```
PE: fastp → bwa-mem2 -p → collate → fixmate → sort → markdup
SE: fastp → bwa-mem2    →                      sort → markdup
```

`--fastq-rev` の有無で自動判定します。

### 2. MACS3 の BAMPE 対応

PE サンプルのピークコールで `-f BAMPE` を使用するように変更しました。BAMPE ではリードの延長モデルではなく、実際のインサートサイズからフラグメント境界を決定します。

- PE: `-f BAMPE`（実際のフラグメント長を使用）
- SE: `-f BAM`（従来通りシフトモデルで延長）

### 3. 統計情報の出力

v1 互換の 15 カラム TSV (`{SRX}.stats.tsv`) を出力するようにしました。

| カラム | 内容 | ソース |
|--------|------|--------|
| $1 | SRX | サンプルID |
| $2 | SE(0) / PE(1) | 自動判定 |
| $3 | FASTQ サイズ | 入力ファイル（PE は両方の合計） |
| $4 | SAM サイズ | 0（パイプ処理のため中間ファイルなし） |
| $5 | リード数 | fastp JSON (before_filtering) |
| $6 | フィルタ後リード数 | fastp JSON (after_filtering) |
| $7 | マップ率 % | MAPPED / READS_AFTER × 100 |
| $8 | Dup 除去率 % | (1 - MAPPED / READS_AFTER) × 100 |
| $9 | BAM サイズ | dedup BAM（削除前に計測） |
| $10 | BedGraph サイズ | BedGraph（削除前に計測） |
| $11 | BigWig サイズ | 出力ファイル |
| $12-14 | Bed05/10/20 本数 | narrowPeak の行数 |
| $15 | Time (分) | 実行時間 |

## BS-seq パイプライン (`pipeline-v2-bs.sh`)

### 1. fastp によるトリミングの追加

abismal の前に fastp による QC・トリミングを追加しました。

- **PE**: fastp が NVMe スクラッチにトリミング済み FASTQ を書き出し、abismal がそれを読む（2つの出力ストリームがあるためパイプ不可）
- **SE**: プロセス置換 `<(fastp --stdout ...)` で abismal に直接ストリーム（ディスク書き込みなし）

BS-seq コンテナ (`v1.1.0`) に `fastp=1.3.1` を追加しました。

### 2. `--genome` 引数の追加

CpG カバレッジの計算にゲノムごとの CpG 数が必要なため、`--genome` 引数を必須にしました。

| mm10 | 43,816,016 |

## その他の確認事項

### 小ゲノムでの 4 cores/job

hg38 では bwa-mem2 のインデックスが約 16 GB/プロセスのため、4 cores/job（32並列）は OOM になりました。しかし ce11 のインデックスは約 0.5 GB のため、4 cores/job でも問題なく動作します。`--threads` はゲノムごとに設定可能です。

### samtools sort のメモリ動作

パイプ処理でも通常のファイル入力と同じ動作です。`-m` で指定したメモリ（スレッドあたり）をバッファとして使い、超過分は `-T` で指定した NVMe スクラッチにスピルします。

## 調査結果

### ENA と NCBI SRA の同期状況

ENA を FASTQ のプライマリソースとして使用する上での遅延を調査しました。

| 項目 | 遅延 |
|------|------|
| メタデータ同期 | 1〜3日 |
| FASTQ ファイル生成 | 約7〜14日（SRA → FASTQ 変換の時間） |

- **2週間以上前のサンプル**: ENA で FASTQ が利用可能（問題なし）
- **直近2週間以内**: メタデータはあるが FASTQ 未生成の場合あり
- **dbGaP（制限アクセス）データ**: ENA には共有されない（ChIP-Atlas の対象外）

**結論**: ENA をプライマリソースとし、FASTQ が未生成の場合は `fasterq-dump` にフォールバックする現在の設計で問題ありません。ChIP-Atlas の 40万サンプルの大部分は過去数年間に蓄積されたものであり、ENA で確実に取得できます。

### SRA Lite ファイルの品質スコア

NIG 上の DDBJ ミラー (`/lustre9/.../dra/sralite/`) にある SRA Lite ファイルの品質スコアについて調査しました。

**SRA Lite は品質スコアを完全に喪失します。** 全リードが一律 Q30（pass）または Q3（reject）に置換され、元の per-base 品質情報は復元不可能です。

| アッセイ | 影響 | 判定 |
|----------|------|------|
| ChIP-seq | 小：MACS3 は品質スコアを使用しない | 使用可能（ただし非推奨） |
| BS-seq | 大：品質ベースのフィルタリング・SNP 判定が不可能 | **使用不可** |

**結論**: SRA Lite パスは使用しません。現在のダウンロード戦略（ENA HTTPS からオリジナル FASTQ を取得、DRR は DDBJ の bz2 オリジナル FASTQ を使用）が正しいアプローチです。
